Creating and Controlling User Accounts


Here we look at user management and administration.

Chapter 6 of the RedHat Linux Systems Administrator's Primer from RHEL 9 Guides on the menu is a very good resource on user management in general, and describes the command line tools available for user management on our TinyNet systems.

Creating Users

useradd is good enough for system accounts (see System Accounts under Server Roles on the menu) but adduser is much nicer for adding regular users. It asks a lot of questions, but just go with the defaults. Eventually you will see 

 New account will be created as follows:
 ---------------------------------------
  Login name.......: 
  UID..............: [ Next available ]
  Initial group....: [ users ]
  Additional groups: [ None ]
  Home directory...: [ /home/login_name ]
  Shell............: [ /bin/bash ]
  Expiry date......: [ Never ]
See the man pages for usermod (to modify user characteristics) and userdel (to delete a user). There is a similar set of utilities for groups: groupadd, groupmod, groupdel

Remember to set a password for each user you create with passwd username. Any trivial password is good enough for now - or try pwgen (on any TinyNet host).

The pwgen utility generates passwords which are designed to be easily memorized by humans, while being as secure as possible. Human-memorable passwords are never going to be as secure as completely completely random passwords, but people tend to write down things that are difficult to remember (like completely randomly generated passwords) and usually rely on a predictable pattern if they are asked to change their password on a regular basis.

The pwgen program is designed to be used both interactively and in shell scripts. Check the man page!

Just to note (since it is a bit hard to find): to automatically set a password with useradd all you need are the openssl libraries: 
   PP=$(openssl passwd -1 net-r.0tt0)
   groupadd -g 234 otto
   useradd -g otto -u 234 -d /var/net-r -c "otto.net-r" -s /bin/rbash -p $PP otto
creates the new user otto with password net-r.0tt0

sudo

The su command ("superuser" or "substitute user") is the standard way for a user logged into one account to temporarily change their identity to another user when they know that other user's password. So, anyone logged in as a normal user can get root privileges if they know the root password. This is a big security risk, known as "privilege escalation".

But, there are times when system administrators want to give some users limited administrative rights - helpdesk personnel who need to solve problems with permissions, or backup operators for example.

An advantage of sudo is that an administrator can allow different users access to specific commands based on their needs, without giving out the root password. By default, sudo requires that users authenticate themselves with their own password. Once authenticated, permitted commands are executed as if by the root user.

Since commands executed via sudo are executed in the user's shell, not a root shell, the root account can be disabled. This is the default for Ubuntu, which is why you see so many helpful instructions predicated by sudo. The logic behind this is that root privileges should be used consciously and cautiously, which is not always the case when people have a root shell.

The argument against sudo is that having a /etc/sudoers that simply says 

%admin ALL=(ALL) ALL
means rather than having one root password to protect, the password for every user in the admin group is a root password, which makes the system much more vulnerable.

A compromise is to define User_Alias and Cmnd_Alias in the /etc/sudoers configuration file, so only certain users are allowed to run a root shell. This means there are still several root passwords but attackers have to guess the username as well as the password.

The bottom line is that higher security means less convenience, and system administrators always need to find a balance between these two conflicting goals.

Whether or not you use sudo, using escape sequences to make a user login prompt green and a root login prompt red
is a great idea: see Prompt Color under Host Management on the menu.


The sudo and sudoers man pages are not the easiest to read - the Configuring sudo page under Documentation on the menu is simpler, but still detailed. This is just a brief, practical introduction.

Warning: /etc/sudoers MUST free of syntax errors! Any error makes sudo unusable.
Always edit it with visudo to prevent errors.
visudo checks the sudoers file after the edit and will not allow saving the file if there is a syntax error.
It also tells you to try again later if someone else is already editing the sudoers file.

If visudo comes up in a strange editor, add a line under the Defaults specification comment that says
    Defaults   editor=/usr/bin/mcedit:/usr/bin/vi
Creating the same setup as Ubuntu is straightforward:
  1. Use the command id -Gn username to check the user's current group membership

  2. Add the user to the existing group wheel with usermod -G wheel,users username
    Names of the groups must be separated with a comma and no spaces. If the user is currently a member of a group which is not in the list, the user will be removed from that group.
    The wheel group has a long history: check the alternate stories of its origin and "wheel wars" at Wikipedia

  3. Verify the groups assigned to the user with id again.

  4. Use visudo to edit /etc/sudoers and uncomment one of the %wheel lines, depending on if you want the user to enter their password again or not.

  5. Go one step farther and add a line to the Defaults section that says Defaults requiretty so sudo can only be run from an interactive login session ("tty" is the name for a screen or "terminal" in the Unix tradition, because originally stdout was a "teletype" printer (tty) rather than a screen). This prevents using SSH for automatic login and execution of commands; see the Smoother SSH page under SSL and SSH on the menu for ways to get around this.

  6. You might also want to try Defaults pwfeedback so you can see something when you put in a password - this is off by default to prevent "shoulder surfers" from seeing the number of characters in your password.
Once you have a working sudo setup, it only takes a few steps to disable root logins and force people to use sudo.
Be Careful: you can lock yourself out if you disable the root password before you know your sudo setup works properly!
  1. Open a new virtual terminal (VT), log in as a normal user in the proper group, and get a root shell with sudo bash
  2. The easiest way to disable the root account is to lock it with passwd -l root
  3. Open another VT and try to login as root to test that it worked.
  4. Switch back to your sudo VT
  5. A similar command unlocks the account: passwd -u root
  6. Again, switch to another VT and try to login as root to test that unlocking the root account worked.
  7. Once you are sure it works, leave the root account locked.

Other Tools

There are a number of other tools that it is useful to know about, but have no practical application in out TinyNets:

Restricted Shell

Restricted shells provide protection to both the system and the user. The system is protected because the user should not have much access to destructive commands. The user is protected damage done to the system using commands not on the path are likely not done by the user. The system manager should be responsible for ensuring the commands on the path do not provide unrestricted shell access. A user always has full access to programs on their path, so giving people the ability to write any files on the path provides an obvious risk.

If bash is started with the name rbash (via a symlink) the shell becomes restricted. It behaves identically to the standard shell with the exception that the following are disallowed or not performed:
  • changing directories with cd
  • specifying command names containing /
  • specifying a file name containing a / as an argument to the . builtin command
  • setting or unsetting the values of SHELL, PATH, ENV, or BASH_ENV
  • redirecting output using the >, >|, <>, >&, &>, and >> redirection operators
However, when a shell script is executed, rbash turns off any restrictions in the shell spawned to execute the script. This includes the files bash reads when it starts up. When bash is invoked as an interactive login shell it first reads and executes commands from /etc/profile, and then looks for
  1. ~/.bash_profile
    The personal initialization file, executed for login shells
  2. ~/.bashrc
    The individual per-interactive-shell startup file
in that order, and reads and executes commands from the first one that exists and is readable. When a login shell exits, bash looks for and executes commands from ~/.bash_logout and /etc/bash.bash_logout, if they exist. These are files are useful for initialising and cleaning up after a restricted login.

chroot Jail

chroot changes the apparent root directory for a running process and its children. This means it cannot name (and therefore not access) files outside the designated directory tree. The modified environment is often called a "chroot jail". This takes some work to set up, but it is often considered worth it for remote logins.

For a chroot process to be able to start successfully, you must populate the chroot directory with all required program files, configuration files, device nodes, and shared libraries at their expected locations relative to the level of the chroot directory. This means copying copy the appropriate binaries and their libraries (use ldd!) into the jail directory tree (e.g., /jail/usr/lib, /jail/sbin, etc.), ensuring that there are no setuid or setgid executables that are owned by root. A program can break out of a chroot jail if it can gain root privilege and use chroot() to change its current working directory to the real root directory.

Rather then manually copying all commands and required libraries, see this article for a very useful script:
http://how-to.linuxcareer.com/how-to-automatically-chroot-jail-selected-ssh-user-logins

That article also shows how to automatically chroot jail selected user ssh logins based on the user group. This technique can be quite useful if you want your user to be provided with a limited system environment and at the same time keep them separate from your main system. You can also use this technique to create a simple ssh honeypot.

The classic use for chroot is ftp. A good reference is http://www.thegeekstuff.com/2012/03/chroot-sftp-setup/

The format of a command to start a service in a chroot jail is 

    /usr/sbin/chroot jailpath /bin/su user daemonname &
with the pathname of the jail directory, the username that runs the daemon, and the path (inside the jail) of the daemon that provides the service.

PAM

PAM, short for Pluggable Authentication Modules, is a system of libraries that allows the local system administrator to choose how individual applications authenticate users. Linux-PAM separates the tasks of authentication into four independent management groups: account management; authentication management; password management; and session management. These groups take care of different aspects of a typical user's request for a restricted service. One of the most common uses of PAM is to provide a "single-sign in" for users by getting their credentials from an LDAP server rather than a local /etc/passwd file.

PAM is NOT like xinetd that encloses and restricts access to some service. An application needs to be "PAM aware", meaning it was been written and compiled explicitly to use PAM. Slackware does not have PAM enabled (up to version 14.2, and possibly beyond). This is at least in part because experimenting with PAM is an easy way to lock yourself out of the system permanently: the system is not accepting your authentication credentials, but you need to log into the system to make the changes needed to prevent you from being locked out.

RADIUS

RADIUS, which stands for "Remote Authentication Dial In User Service", is another application that supports centralized authentication. RADIUS specialises in AAA (Authentication, Authorization, Accounting) for equipment such as wireless access points, and is often the back-end of choice for802.1X Port-based Access Control authentication as well.
  • Authentication: If the user can access the equipment.
  • Authorization: Level of access to the equipment.
  • Accounting: What the user is doing
RADIUS servers receive user connection requests, authenticate the user, and then return the configuration information necessary for the client to deliver service to the user. Servers can typically use a number of data sources, including text files, LDAP servers, SQL databases, and even PAM; they also typically support different types of encryption, depending on the authentication architecture in place.

RADIUS is often used in enterprises to manage access to the Internet, internal wireless networks, virtual private networks (VPNs), network ports, and to facilitate roaming by issuing a single set of credentials that are usable on many networks. Most sites need complex policies, interactions with databases, and logging. Switches and Access Points are typical RADIUS clients. The bottom line is that while we could set up RADIUS on our TinyNet, without actual hardware it is too minimal to be meaningful (iwconfig reports that Virtualbox Host-Only adapters do not have wireless extensions).

Brain Teaser

Best practice recommends that users keep changing their passwords regularly. But typically users won't change their password unless they are forced to.

It's the system administrators responsibility to find a way to force them to change their password, but putting a gun on their head is not an option! (even though the most security conscious sysadmins may be tempted to do that).

Here is the basis of a script to automatically change a user's password if it is more than one day old. Save this from your browser, or download it with wget http://www.my-tiny.net/pwchg.sh.txt

It's a brain teaser because you not only need to finish it and test it, you also need to figure out how to use it. Ideally we could run it every time the user logs in or logs out, so the user is assigned a new password frequently - but how? Should it be used for every account on the system? only for our "sudoers"? only for the "root-shell sudoers"? What could go wrong?

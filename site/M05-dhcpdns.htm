Host Name Resolution


First, the essentials:
  1. There are three files that are used for name resolution (address to name mapping):
    Any host name used in a configuration file needs to be in one of these places.
    /etc/HOSTNAME    all systems the "official" or "baseline" name, only one line here
    /etc/hosts    all systems lists of alternative names or "aliases" for IP addresses
    /etc/dnsmasq.d/cnames    gateway only    list of alternative names or "aliases" for official names
  2. Every host on the network must have
    (See Linux Notes::Network Basics for a hands-on exercise)
    • IP address (uniquely identifies the host on the network)
    • Netmask (defines the local subnet / layer 3 "broadcast domain")
    • Default route (address of a system that knows how to get beyond the subnet)

  3. Commonly used dhcp options
    • option subnet-mask mask
      Specifies the subnet mask in dotted decimal notation.
    • option broadcast-address address
      Defines the broadcast address for the client's subnet.
    • option domain-name domain
      Defines the domain part of the FQDN (everything except the HOSTNAME).
    • option domain-name-servers address [ , address ...]
      Lists the Domain Name System (DNS) name servers the client should use, in order of preference.
    • option routers address [ , address ...]
      Lists the routers the client should use, in order of preference. Also used to set the default route.
    • option static-routes destination gateway [ , destination gateway ... ]
      Lists the static routes the client should use.

TinyNet dnsmasq

Nowadays, /etc/hosts is considered a fallback for when the DNS is not running. It only sets the localhost address on all of our systems except the Gateway. Two reasons for this: since it is the gateway between subnets it needs to have one interface with an IP address on each subnet; and since it runs the DNS and DHCP server, it makes sense to have its own addresses and names set outside that service.

One thing to know is that on all Linux systems, names in /etc/hosts without a dot give inconsistent results - sometimes they work and sometimes they don't. The reason is buried deep in the system call code, and will probably never be changed.

We use dnsmasq because it does two things well: DHCP server and nameserver. They are closely related, but we can pick them apart.

When dnsmasq starts, it reads /etc/hosts on the local system along with its configuration files in /etc/dnsmasq.d/ . Names for the gateway interfaces come from /etc/hosts: 
192.168.56.101    neta-gw.tinynet.edu    net-a.tinynet.edu   gw
192.168.66.101    netb-gw.tinynet.edu    net-b.tinynet.edu
192.168.76.101    netc-gw.tinynet.edu    net-c.tinynet.edu   gateway
Names for the other systems come from the client DHCP requests (dhcpcd), that use /etc/HOSTNAME on the local system in a special way.

For example with ldap-nb.net-b.tinynet.edu in /etc/HOSTNAME, the localDHCP function in /etc/rc.d/rc.inet1 starts the DHCP client with:

/sbin/dhcpcd -i $NNOM -h $HNOM -F both $ETH

and in the DHCPDISCOVER message dnsmasq sees 
        vendorclass = net-b
        hostname = ldap-nb
        update FQDN 
        update PTR
        assign a dynamic address
dnsmasq processes these instructions using directives in /etc/dnsmasq.d/ There are lots of comments in those files, but let's look at the key directives here.

First, assign a dynamic IP address. We want this done based on the subnet, so in /etc/dnsmasq.d/dhcp we have several directives with a string to match, a range for address assignment, and a lease time for the address 
    dhcp-vendorclass = netA, net-a
    dhcp-vendorclass = net-B, net-b
    dhcp-vendorclass = netC, net-c

    dhcp-range = net:netA, 192.168.56.102, 192.168.56.252, 12h
    dhcp-range = net:net-B, 192.168.66.102, 192.168.66.252, 12h
    dhcp-range = net:netC, 192.168.76.102, 192.168.76.252, 12h
An address to use with route add default gw is also passed back 
    dhcp-option = net:netA, option:router, 192.168.56.101
    dhcp-option = net:net-B, option:router, 192.168.66.101
    dhcp-option = net:netC, option:router, 192.168.76.101
Since these are interfaces on the gateway and dnsmasq is there, this address also works to identify the default nameserver

In /etc/dnsmasq.d/dns we set dnsmasq to always record the Fully Qualified Domain Name (FQDN) in its lookup tables. Then we set different domains for the subnets, so queries in these domains are answered from /etc/hosts or DHCP only. This is equivalent to the SOA record in a "real" (ISC bind) setup. 

    dhcp-fqdn

    domain = tinynet.edu
    domain = net-a.tinynet.edu, 192.168.56.0/24
    domain = net-b.tinynet.edu, 192.168.66.0/24
    domain = net-c.tinynet.edu, 192.168.76.0/24

    local = /tinynet.edu/
    local = /net-a.tinynet.edu/
    local = /net-b.tinynet.edu/
    local = /net-c.tinynet.edu/
We use /etc/dnsmasq.d/cnames to define aliases for the hosts that request dynamic addresses 

    cname = webmail.tinynet.edu, web-na.net-a.tinynet.edu
    cname = ldap.tinynet.edu, ldap-nb.net-b.tinynet.edu
    cname = mailhost.tinynet.edu, mail-nc.net-c.tinynet.edu
Nothing more really: "Resource Records" are the basic information element of the DNS, and PTR records are for querying the DNS server with an IP address and getting back the name (called "reverse lookup"), which dnsmasq does "automagically", saving us some work - we have to do this by hand for each one in a "real" (ISC bind) setup. A MX (Mail eXchanger") record returns the fully qualified domain name of a mailserver for a site. When an e-mail message is sent through the Internet, the sending mail transfer agent (MTA) sends out a DNS query for the MX records of each recipient's domain name, which returns a list of host names for servers accepting incoming mail for that domain, so the MTA can attempt to establish a SMTP connection.

The "reference implementation" of DNS that runs the global Internet root name servers is called "bind", and is maintained by the Internet Software Consortium (ISC). ISC also maintains a reference implementation of DHCP. There is a very good explanation of how to configure the ISC versions to get the same functionality as dnsmasq at
http://blog.bigdinosaur.org/running-bind9-and-isc-dhcp/

Resolving Service Configuration Issues


The quick list of Things To Do:
  1. Look for what you recognise, especially in the log files, starting at the end

  2. Always maintain a working configuration as a backup

  3. Do one thing at a time, and then test it

  4. Do the simplest thing first: pay attention to the "Four P's"

The most common causes of problems with service configuration come down to Permissions, Paths, Ports and Parsing.
  1. Permissions: A common cause of errors is that the owner of a file and the owner of the process that needs to use it do not match. Check the configuration file for a Run As or uid directive, and make sure this user can read (and write / execute where appropriate) all of the files and directories it needs. If a directory is the problem, you may want to make it world writeable with the sticky bit set (1777, drwxrwxrwt) so anyone can write files, but files can only be modified or deleted by the owner. Copying files between systems (especially using SSH) may change the owner of the file on the destination, so be sure to doublecheck.

  2. Paths: Sometimes a program will fail with a message like Exiting - could not load shared library libres.so.0. It is quite possible the file actually exists, but with a different path or name than the one that existed when the source code was compiled. To display the shared libraries required by a program run ldd (List Dynamic Dependencies) like this:

    ldd /path/to/executable

    If ldd reports missing libraries, search for the missing pieces with

    find / libname*

    where libname is the library name from the error message before any dots or numbers.

    If it exists, fix it with a symlink to the path specified in the error message, or a symlink in /usr/lib if it is not already there. Lots of times there is an existing library with a name like libxyz.so.2.0.0 when the program wants libxyz.so so this is pretty easy.

  3. Ports: If htop shows the service is running, use netstat -tulpn to make sure it is listening on the port you expect. If it is and your firewall is on, run appropriate iptables -I INPUT and OUTPUT commands to temporarily "poke a hole in the firewall", and fix your firewall rules after you get it running. Connect to the server using telnet or netcat, and try a few commands from the protocol.

  4. Parsing: Check your typing and punctuation! Also remember that some programs (bash and OpenLDAP for example) are sensitive to trailing whitespace, so use the mc editor and look for those faint blue markers that show spaces and tabs at the end of a line.

Stopping stuff:

In an interactive terminal session, Ctrl c means "stop whatever you are doing". Technically, it sends the INT ("interrupt") signal, which by default terminates an application.

Ctrl d on a line by itself means "flush the input I typed so far", and since the line is empty, read() will return zero, which is interpreted as "end of file". It has no effect if the program isn't reading input from the somewhere.

So, to stop something first try q to quit, then x to exit, then Ctrl d to stop nicely, and finally Ctrl c to just stop whatever the consequence. After a while you will get used to which one works best for which program.


The developers at freeradius.org offer useful advice that applies to every server, not just theirs ...

These steps outline the best known method for configuring the server. Following them lets you create complex configurations with a minimum of effort. Failure to follow them leads to days of frustration and wasted effort.
  1. Start with a "known working" configuration, such as supplied by the default installation.
  2. Find out where the server logs are, and set the log level to info or debug
  3. Make one small change to the configuration files.
  4. Start the server - use debugging mode if there is one
  5. Verify that the results are what you expect
    • The debug output shows any configuration changes you have made.
    • Databases (if used) are connected and operating.
    • Test packets are accepted by the server.
    • Packets are being processed as you expect.
    • The response packets contain the attributes you expect to see.
  6. If everything is OK, save a copy of the configuration, stop the server, and go back to step (3).
When things go wrong,
  1. Double-check the configuration changes, especially your typing and punctuation
  2. Search the debug output for words like error or warning. These messages usually contain descriptions of what went wrong, and suggestions for how it can be fixed.
  3. Sit back, relax and give the problem some thought
  4. Try to find an answer by
    • reading the man page and the "related" pages listed at the bottom
    • reading whatever documentation you can find in /usr/doc, /usr/share/doc, /usr/local/doc, /usr/local/share/doc.
    • using the error message as search terms in Google
  5. Try replace your configuration with a saved copy of a "known working" configuration, and start again. This process can clean up errors caused by temporary edits, or edits that you have forgotten about. Compare these log files to the problem ones - this will highlight the point where the problem arises.

One of the things you will notice is that in dialogs between developers and users, people frequently refer to log files and configuration files. When you ask for help, include a description of what you are trying to do, and the entire debugging output, especially output showing the server receiving and processing test packets. If you do not, you are making it impossible for anyone to help you. However, be sure to scrub shared secrets, passwords, etc. from the output before posting it.

Many people find that when they start writing down the things they have done to try and solve a problem with a view to submitting a request for help or bug report that they end up solving the problem. So, get in the habit of taking detailed notes, and keeping copies of working configuration files so you can "back up" if something breaks.

Collaboration is a very useful way of increasing your experience and problem solving ability. Helping each other to diagnose problems, evaluate solutions, and learn from mistakes is being an active member of our local community. Giving direct answers to assessment questions is cheating.

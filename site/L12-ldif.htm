Adding a new DIT to the LDAP Directory


DIT stands for Directory Information Tree. The entire LDAP database is called the DIT, and OpenLDAP will manage several databases (DITs) for us. Attributes o ("organisation") and dc ("domain component" ) are commonly used to define the base or root of the DIT. Our slapd.conf is already configured for to handle the o=tinynet.edu DIT, and a second dc=tinynet,dc=edu DIT is easy to add.

Be sure to check the LDIF and the DIT section in the LDAP Concepts page under Configure LDAP on the menu for an explanation of LDAP concepts and terms!

Before we start configuring, let's take a side-by-side look at the top levels of our two DITs: 
DIT 1: topclass-o.ldif		DIT 2: topclass-dc.ldif
dn: o=tinynet.edu			dn: dc=tinynet,dc=edu
objectClass: top			objectClass: top
					objectClass: dcObject
objectClass: organization		objectClass: organization
o: tinynet.edu				o: MyTinyNet
					dc: tinynet
description: LDAP Root			description: LDAP Root

   ...					   ...
 
dn: ou=UserNetC,o=tinynet.edu		dn: ou=UserNetC,dc=tinynet,dc=edu
ou: UserNetC				ou: UserNetC
objectClass: top			objectClass: top
objectClass: organizationalUnit		objectClass: organizationalUnit
description: User on Net-C		description: User on Net-C
objectClass: dcObject permits the dc attribute to be present in an entry. It is typically used in conjunction with another one such as organization or organizationalUnit (we'll skip the "why" for now, since it has to do with how object classes are defined as structural or auxiliary). Since the topclass-dc.ldif is ready, all we need to do is define the new DIT and change the DNs for our user entries before we add them to the new database - Simple!

phpLDAPadmin (PLA) is a good way to manage users, but it has problems putting fields in a sensible order in the template that require some "code surgery" to fix. An easy way to use our sample data is to get /etc/openldap on both sides in mc, use [F5] to make a copy of userdata-o.ldif called userdata-dc.ldif, and then use [F4] to edit the new file and change the dn for each user: 

dn: cn=Barbara Jensen,ou=UserNetB,dc=tinynet,dc=edu
ou: UserNetB
cn: Barbara Jensen
objectClass: top
objectClass: person
objectClass: organizationalPerson
objectClass: inetOrgPerson
mail: b.jensen.dc@net-b.tinynet.edu
givenname: Barbara
sn: Jensen
uid: bjensen.dc
title: Account Executive
userPassword: {PLAIN}LetMeIn
Another good change is to add .dc before the @ in the mail: address. If you also add .dc to the uid: then mail for this address will be put into a new mailbox, otherwise there will be one mailbox for both o=tinynet and dc=tinynet,dc=edu messages, since Dovecot uses the uid: to deliver, not the email address.

IMPORTANT notes about editing LDIF

OpenLDAP is obnoxiously unforgiving about whitespace, and the error messages from slapd are typically vague and almost useless.
  • Parent entries must be listed before their children in the file, so that when the server process the LDIF text, it will create the parent entries before the children entries.

  • There must be AT LEAST ONE blank line before each line starting with dn: except - there MUST NOT be ANY blank lines before the FIRST entry in the .ldif file. This is VERY important - strange errors will result otherwise.

  • Comments are indicated by a # as the FIRST character of the line ONLY, otherwise # is taken as content

  • The space following the  :  on each line is VITAL

  • An LDIF line can be split over two lines if there is NO TRAILING WHITESPACE at the end of the first line and the next line starts with EXACTLY ONE SPACE.
In general, you want to make sure there is no whitespace at the end of ANY line!
(watch for the faint blue dots in the mc editor)

Configuring the new DIT in slapd

slapd will not start if any of the databases in slapd.conf are not properly configured, so the first step is to stop the slapd service on the LDAPserver.

USE ONLY THIS COMMAND TO STOP LDAP   /etc/rc.d/rc.slapd stop
DON'T USE KILL PROCESS IN HTOP since it can damage your database

[ 1 ]  Now we can add the database definition for our new dc= DIT by adding /etc/openldap/slapd-db2.conf to the end of slapd.conf. We could do this by copy/paste with the mc editor, but it is soooo much easier to do it at the command line. To be safe, copy /etc/openldap/slapd.conf to /temp as a backup, then enter this command:

cd /etc/openldap; cat slapd-db2.conf >>slapd.conf

Briefly, here we use  ;  to string together two separate commands, and  >>  to write the output of the cat command to the end of slapd.conf (see the pages under Standard I/O on the menu for more details).



[ 2 ]   To accommodate PLA we need to configure anonymous access. Just like before, make the same change in the dn = "cn=LDAPAdmin,dc=tinynet,dc=edu" section at the bottom of slapd.conf 
#---%<---------------------------------------------------------------
# Next backend database definition
        bla bla bla
access to *
       by dn="cn=LDAPAdmin,dc=tinynet,dc=edu" write
       by self   write
       by *      read
Now test the configuration without testing the database configurations:

slapd -Tt -u



[ 3 ]  Next step is to add the database structure. There are two sets of utilities for doing this, a set of ldap commands to use when slapd is running, and a set of slap commands to use when is is stopped. Let's keep it stopped:

slapadd -n 2 -l /etc/openldap/topclass-dc.ldif

Just for reference, -n 2 says "add to our second database" and -l (Careful - use lowercase L not one!) says "using this LDIF file".



[ 4 ]  To make sure everything goes smoothly, enter this command to change the owner and group of all of the newly created database files to the proper system account (we could do this one-by-one with mc - but why?)

chown ldap:ldap /var/ldapdata/dc_tinynet/*

Now use [Up-Arrow] to get the command back, and change it to (Careful - use lowercase L not one!):

ls -l/var/ldapdata/dc_tinynet/*

Note that if you miss this and the database files have the wrong owner, you will get a (typically cryptic) error message like this when slapd refuses to start: 
hdb_db_open: database [...] alock package is unstable
Now test the configuration including the database configurations:

slapd -Tt



[ 5 ]  Now we can add the data. Use [Up-Arrow] to get the slapadd command back, and change it to:

slapadd -n 2 -l /etc/openldap/userdata-dc.ldif

** For reference, the ldapadd version of this command that we would use when the server is running is at the bottom of the page.



[ 6 ]  All Done! Start the server

/etc/rc.d/rc.slapd start

and try some "anonymous bind" queries like these - type in all of the first one, then just use [Up-Arrow] to get the command back and edit it.

ldapsearch -LLL -x -b "dc=tinynet,dc=edu" description
ldapsearch -LLL -x -b "dc=tinynet,dc=edu" "(ou=UserNetA)" description
ldapsearch -x -b "dc=tinynet,dc=edu" "(ou=UserNetA)" cn uid mail
ldapsearch -x -b "dc=tinynet,dc=edu" "(ou=UserNetB)" cn uid mail
ldapsearch -x -b "dc=tinynet,dc=edu" "(ou=UserNetC)" cn uid mail 

The basic syntax is ldapsearch -flags filter attrs
  -x    means use simple authentication instead of SASL 
          openLDAP defaults to SASL authentication - but it takes a lot of configuration
          this is required even for anonymous bind
  -b    specifies the the start point of the search (base-dn)
  -LLL  means to use the simplest LDIF format for output

The basic syntax for a (optional) search filter is "()" or '()' 
attrs is a space separated list of attributes to be returned (also optional).
Normally we will use dovecot, squirrelMail and PLA to search the directory, but command line ldapsearch is good for testing and debugging, and it can be important to understand basic search filter syntax to configure some applications to use LDAP.


Configuring our Applications to use the new DIT

We have to make changes to the same two configuration files as before for Dovecot on the MailHost, and change two on the WebServer: one for Squirrelmail and one for phpLDAPadmin (PLA).

On the MailHost,

Get /etc/dovecot on both sides of mc and use [F5] to copy and rename ldap-dn_o.dbconf to ldap-dn_dc.dbconf (just type the new filename in the destination field).

Use [F4] to edit the file, and make these two small changes: 

# Tell Dovecot to bind to the LDAP directory using these credentials
# Make sure this matches something in the directory or slapd.conf
dn = cn=LDAPAdmin,dc=tinynet,dc=edu
dnpass = slapmesilly

# LDAP search base: where to start searching through the directory
base = dc=tinynet,dc=edu
scope = subtree
Save that file, and open /etc/dovecot/dovecot-auth.conf;
uncomment the passdb { and userdb { blocks for ldap-dn_dc.dbconf in the section at the bottom.

Finally, stop and restart Dovecot to get the new configuration in place.



On the WebServer,

Edit /var/www/squirrelmail/config/svr_ldap.php to use the new DIT (look for the helpful comment you added!) 
// This is a sample block to edit when we add another DIT
// Be sure to increment (add one to) the $ldap_server[ ] array index!

    $ldap_server[1] = Array(
        'host' => 'ldap.tinynet.edu',
        'name' => 'ldap dc=tinynet,dc=edu',
        'base' => 'dc=tinynet,dc=edu'
    );


Then edit /var/www/ldapadmin/config/config.php to use the new DIT by uncommenting the relevant lines in the * Next Server section.

In this case ALL of the lines starting with # are relevant EXCEPT 
# $servers->setValue('server','host','127.0.0.1');
which should remain commented out until you get stunnel ready.
All of the lines starting with /* are documentation comments, so leave them as they are ...

When you finish, stop and restart the WebServer to get the new configurations in place, and test it out in your Windows browser.

If something goes wrong

If you accidentally corrupt your dc= database, just
  1. Stop slapd (this first step is most important)
  2. Use mc to go to /var/ldapdata and
  3. Delete all of the files in the dc data directory except DB_CONFIG
Then
  1. Copy the backup slapd.conf from /temp to /etc/openldap
  2. Add the database definition for the dc= DIT to slapd.conf
  3. Continue with steps 2-6
Careful: if you delete the files before you stop slapd you will never get LDAP to start again!

** For reference, when the server is running we use this command to add data:

ldapadd -x -D "cn=LDAPAdmin,dc=tinynet,dc=edu" -w slapmesilly -f /etc/openldap/userdata.ldif 
-x  means use simple authentication instead of SASL 
      openLDAP defaults to SASL authentication - but it takes a lot of configuration.
-D  specifies the distinguished name with which to authenticate to the server,
-w  specifies the associated password (use -W to prompt for the password)
      -- these are the rootdn and rootpw we specified in slapd.conf --
-f  specifies the full path to the LDIF file (not -l like slapadd!)

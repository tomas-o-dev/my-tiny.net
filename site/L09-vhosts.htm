Virtual Servers with Monkey


This version of Monkey webserver has a very simple configuration file, with all the same essential features as production strength servers like Apache, Lighttpd, and IIS but without all of the distractions.

Virtual Servers allow one webserver process to handle multiple websites. This is very common, so it is useful to understand how to set them up.

It used to be common to see websites with URLs with a /~username/ which meant it was a personal website. The UserDir directive is for this style, allowing users to serve web pages from a directory under their home directory.

It is much nicer, though, to comment out the UserDir directive and give users their own Virtualhost. This requires some modifications to the monkey configuration file along with new cnames for them, creating some directories and changing the owner and permissions, and setting up cron jobs (Scheduled Tasks in Windows) to copy files for better security.

[ 1 ]  Setting up the VirtualHosts and cnames

Open /etc/monkey/monkey.conf in the mc editor with [F4] and move down to the Virtualhost section.

Press [F3] and look for [B---] in the top status bar which means you are marking a block. Use the arrow keys to highlight from the <Virtualhost> tag to the </Virtualhost> tag, and press [F3] again at the end of the block.

Press [Enter] to open a blank line (top status bar will now show [BM--]), and press [F5] to paste in the block. Then press [F3] until the top status bar just shows [-M--] (twice is usually enough), which means you have stopped marking blocks of text.

(yes, that's clunky, but mc does so many good things we just have to forgive this one)

Now edit the directives to create a new site: 
      <Virtualhost>
           VirtualServerName arnie.tinynet.edu
           VirtualDocumentRoot /var/monkey/vhosts/arnie
           VirtualScriptAlias /cgi-bin/ /var/monkey/vhosts/arnie/run/
           VirtualForceGetDir off 
      </Virtualhost>
Save this, and create the VirtualDocumentRoot and VirtualScriptAlias directories. Then change the owner and group for each new directory to nobody (the owner of the monkey process), and change the permissions so that only the owner can Read+Write+Execute [700].

Final step is to restart the monkey webserver process.

Now move over to your Gateway and edit /etc/dnsmasq.d/cnames. Find the cnames for the Webserver, copy one and paste it in below, and put the VirtualServerName in the first half of the line - like this: 
      arnie.tinynet.edu, lecture-web.net-a.tinynet.edu
Save the file and restart dnsmasq with
/etc/rc.d/rc.dnsmasq stop and
/etc/rc.d/rc.dnsmasq start

You can have any number of Virtualhost blocks in monkey.conf, as long as each one has a unique VirtualServerName and a matching cname in the DNS.

[ 2 ]  Setting up user accounts

See the Creating Users section in the User Accounts page under Host Management on the menu for how to create an account for arnie with adduser.

Once the account is created, open a new virtual terminal, log in as arnie, and create a new webpages directory with another run directory under it in the home directory. Check the permissions to make sure that arnie is the owner, and only the owner can write to these directories.

Now arnie can log in with a SFTP (ssh) client and drop his pages in ~/webpages, and his CGI scripts in ~/webpages/run. The corresponding directories under his VirtualDocumentRoot can only be accessed by the user that owns the webserver process (nobody), so we need a way to move new uploads from the home directory to the VirtualDocumentRoot. We take care of this with cron jobs (Scheduled Tasks in Windows).

[ 3 ]  Scheduling Tasks With cron

The cron service (daemon) runs in the background and constantly checks the lists in the files in the /var/spool/cron/crontabs directory for jobs to be done. Confusingly enough, these files are referred to as crontabs, and the command to create and edit the job lists inside the file is called (you guessed it) crontab.

The format of the crontab entries is simple: five time fields separated with spaces or tabs, followed by the command to be executed and any parameters it needs. 

      |================ [1] Minute (0 - 59)
      | |============== [2] Hour (0 - 23)
      | | |============ [3] Day of month (1 - 31)
      | | | |========== [4] Month (1 - 12) 
      | | | | |======== [5] Day of week (0 - 7) (Sunday = 0 or 7)
      * * * * * /path/to/command parameters
Operators:

* specifies all possible values for a field. For example, * in the month field (4) means every month.
, specifies a list of values. For example, 1,2,3,4,5 in the day of week field (5) means run only on weekdays.
- specifies a range of values. For example, 1-5 in the day of week field (5) means run only on weekdays
/ specifies a step value. For example, */10 in the minutes field (1) means run every 10 minutes
Note: cron does not deal with seconds. Day of month and day of week fields are an or condition - when either field is true it will be executed. The crontab man page has more examples.

Some important restrictions to take note of:
  • Each user can have their own crontab file, and the jobs run from it are executed as that user.
  • The crontab files have to be regular files or symlinks to regular files, and they must not be executable or writeable by anyone else than the owner.
  • Setting paths, environment variables, etc. must be done in the script cron is calling.
  • Absolute path names for commands, like /bin/ls should always be used.
To create or edit your crontab:    crontab -e
After you save and exit from the editor, the new crontab will be installed automatically.

To list all your cron jobs:    crontab -l     (lowercase L not one)
To see the cron logs:    cat /var/log/cron


The existing /var/spool/cron/crontabs/root uses the run-parts command to run the scripts or programs in a directory. This makes it easy: we can put executable scripts into the /etc/cron.{daily or hourly} directories to designate cron jobs (be sure to set the execute bits).

So, when we have a root login we have two ways to move the files out of our user's home into the webserver VirtualDocumentRoot directories:

use crontab -e to create jobs in the root crontab to run every ten minutes, for example: 
# move user Virtualhost files to the VirtualDocumentRoot
*/10 * * * * mv -f $(find /home/arnie/webpages -maxdepth 1 -type f) /var/monkey/vhosts/arnie
*/10 * * * * mv -f $(find /home/arnie/webpages/run -type f) /var/monkey/vhosts/arnie/run
or put a script like this into the /etc/cron.hourly/ directory (make sure owner is root and the execute bits are set) 
#!/bin/sh
# move user Virtualhost files to the VirtualDocumentRoot
mv -f $(find /home/arnie/webpages -maxdepth 1 -type f) /var/monkey/vhosts/arnie
mv -f $(find /home/arnie/webpages/run -type f) /var/monkey/vhosts/arnie/run
We have to use find -type f to move only the files, otherwise the first mv command will move the run directory too! We also need maxdepth 1 or all the files in run will get moved to the top directory.

Running a task as exactly as cron would run it is tricky: cron is designed to run in a non-interactive shell with no attached input terminal and a modified environment, and possibly also requires a specific shell (like bin/sh instead of /bin/bash). That means testing is a slow process because the best way to test is just wait.

Version Note:
mytyVM uses "dillon's cron", which is similar to the "vixie cron" used by other Linux distributions, but simpler. Debian and Redhat also have /etc/crontab for system jobs, with an extra field to specify the user to run as. On these systems cron treats the files in /etc/cron.d as extensions to /etc/crontab - on mytyVM systems /etc/cron.d stays empty.

[ 4 ]  Setting up the user site

Now you can start links on the Gateway, press Esc to get the menu and select File and Go to URL. Type in http://arnie.tinynet.edu/ to get the site.

When the VirtualDocumentRoot is empty, links shows the site name and says "Forbidden". So, we know we got to the right place, but there is nothing to serve up!

Use mc to copy the file index.html from /var/monkey/htdocs to /home/arnie/webpages. Use [F4] to edit arnie's copy, and change the part that says Monkey is running in your system to You have reached Arnie's homepage (or whatever you like).

Now the hard part: wait for the cronjob to execute (just relax and enjoy the break!).

When index.html shows up in the VirtualDocumentRoot, go back to the other VM running links, press Esc to get the menu and select File and Reload. Smile and be happy!


Enhanced cron

That is enough for proof-of-concept, but there is a flaw in our cron strategy: what happens when our user wants to have more directories to organise their site pages and images? And we really do not want to force ourselves to update the cron job list every time we add a new user.

Here is a script that will check every directory in /home, and move all of the files and directories under webpages to our VirtualDocumentRoot (uncomment the lines in blue and comment out the move line in red to see it in action)

/usr/local/bin/mvUserSites.sh 
    #!/bin/sh
    # move user Virtualhost files to the VirtualDocumentRoot
    WPD=$(find /home -maxdepth 2 -type d -name 'webpages')
    # echo $WPD
    for DN in $(echo $WPD); do
       # echo $DN
       WPF=$(find $DN -type f)
       # echo $WPF
       for SF in $(echo $WPF); do
          DF=$(echo $SF |sed 's:^/home:/var/monkey/vhosts:' |sed 's:/webpages::')
          DD=$(dirname "${DF}")
          if [[ ! -d $DD ]]; then
             mkdir -p $DD
          fi
          # echo "move $SF $DD"
          mv -f $SF $DD
          ## change owner:group? permissions? 
          ##   $DF is destination file, $DD is destination directory
       done
    done
  1. variable WPD is a list of all the webpages directories under a user home directory
  2. the first "for" loop moves through the WPD list
  3. variable WPF is a list of all the files in the webpages directories
  4. the second "for" loop moves through the WPF list
  5. the first sed replaces /home with our top VirtualDocumentRoot, the second deletes /webpages from the path,
    and the outcome is stored in the variable DF
  6. dirname is a handy way to get the path without the name of the file
  7. if the directory does not exist, mkdir -p will create all of the directories in the path
  8. and now we can move the source file to the destination directory
After we name the script mvUserSites (for example), and make sure owner is root and the execute bits are set, we can put this script in /etc/cron.hourly/ to have it run every hour, or if we want to run it more often we could put it in a new directory /etc/cron.vhosts/ (for example) and replace the two lines we added to the root crontab with this one: 

# move user Virtualhost files to the VirtualDocumentRoot
*/5 * * * * /etc/cron.vhosts/mvUserSites

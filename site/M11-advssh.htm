Smoother SSH Connections


SSH has become a standard for remote host administration because it provides secure communication over the network. There is a lot you can do with SSH. A helpful reference is: http://docs.slackware.com/howtos:security:ssh

However, we always have to deal with the tradeoff between security and usability: more security requires stronger and more frequent authentication. Tweakng the SSH configuration to allow connections without entering usernames and passwords is not too difficult, and can be quite convenient when making frequent SSH connections.

OpenSSH Configuration Files

OpenSSH has two different sets of configuration files: one for the server daemon (sshd) and one for client programs (ssh, scp, and sftp).

System-wide configuration information is stored in /etc/ssh/

sshd_config
The configuration file for the sshd daemon.
ssh_config
The system-wide default SSH client configuration file.

sshd_config and ssh_config can contain any options that you would use on the command line to specify connection parameters, allowing common connection parameters to be used automatically on connection. It is always possible to override the values defined in the configuration files through flags on the commands line. Refer to How To Configure Custom Connection Options for your SSH Client and the man pages for sshd_config and ssh_config for information about the various directives available .

moduli
This file contains Diffie-Hellman groups used for the Diffie-Hellman key exchange which is critical for constructing a secure transport layer. When keys are exchanged at the beginning of an SSH session, a shared, secret value is created which cannot be determined by either party alone. This value is then used to provide host authentication.

ssh_host_rsa_key
ssh_host_rsa_key.pub
The RSA private key and public key used by the sshd daemon for version 2 of the SSH protocol. There may also be ssh_host_dsa_key(.pub) for DSA encryption and/or ssh_host_key(.pub) which is the RSA key pair used for version 1 of the SSH protocol.

User-specific SSH configuration information is stored in the user's home directory
under a directory known as ~/.ssh/ or $HOME/.ssh/

config
Each user on the system can maintain a client-side SSH configuration file. Any system-wide default is overridden if the directive is also here.
authorized_keys
This file holds a list of authorized public keys for servers. When the client connects to a server, the server authenticates the client by checking its signed public key stored within this file.
known_hosts
This file contains public key data of SSH servers accessed by the user. This file is very important for ensuring that the SSH client is connecting the correct server.
id_rsa
id_rsa.pub
The RSA private key and public key used by the ssh client for version 2 of the SSH protocol. There may also be id_dsa(.pub) for DSA encryption and/or identity(.pub) which is the RSA key pair used for version 1 of the SSH protocol.

Note: If a server's host key has changed, the client may notify the user that the connection cannot proceed until the server's host key is deleted from the known_hosts file. To remove a stale entry, use ssh-keygen -R host -f ~/.ssh/known_hosts

SSH and SUDO

An advantage of sudo is that an administrator can allow different users access to specific commands based on their needs. By default, sudo requires that users authenticate themselves with their own password. Once authenticated, permitted commands are executed as if by the root user, and the root password can be disabled (this is the default for Ubuntu, which is why you see so many helpful instructions that start with "sudo").

See the Host Management :: User Accounts page on the menu for how to configure sudo.

To prevent root logins via SSH, edit /etc/ssh/sshd_config and change PermitRootLogin to no. This forces users with an ssh remote login to use su or sudo to run commands with root privileges.

When requiretty is set in /etc/sudoers, sudo can only be run from a login session ("tty" is the name for a screen or "terminal" in the Unix tradition, usually held to be short for Teletype). By default, when you ssh without a command to execute (just to log in), a "pseudo tty" is allocated automatically. When you specify a command to execute that is not just plain text output, you need to tell ssh specifically to open a tty for you, like this: ssh -t user@host.name htop.

We need to do the same thing when sudo requires a tty:
ssh -t user@box.example.com "sudo -n -u user -c runcommand"

The -n option to sudo will prevent sudo from prompting for a password, but if the command requires a password you'll get an error. To get around this, set up Multiplexing or Key Based Authentication.


Setting up ssh Multiplexing

Multiplexing is the ability to send more than one signal over a single line or connection. OpenSSH can re-use an existing TCP connection using multiplexing. This enables the sharing of multiple sessions over a single network connection. These sessions will try to reuse the master connection to the remote server rather than initiating new ones, but will fall back to connecting normally if the control socket does not exist, or is not listening.

Multiplexing can be configured in either ~/.ssh/config (ssh client configuration file) or /etc/ssh/ssh_config (system wide settings)

To reuse a ssh connection for all hosts: 

host *
    ControlMaster auto
    ControlPath /tmp/ssh-%r@%h:%p
    ControlPersist 3600
ControlMaster enables multiplexing. When you have one active SSH session in a separate virtual terminal, you can open another connection to the same server without having to input a password or anything else.

ControlPath specifies the path to the control socket used for connection sharing. The remote login username will be substituted for %r, the target host name for %h, and the port for %p, to ensure that shared connections are uniquely identified.

ControlPersist keeps the control socket open for the specified number of seconds (3600 is one hour) after the original connection is closed. In other words, to need to start with a session where you log in with username and password, but you can stop that one immediately. Any new session within ControlPersist seconds will not require logging in.

You can match any host in the 192.168.0.[0-9] range with host 192.168.0.? or any host in a domain with host *.domain.name

Once multiplexing is configured:
To connect as usual (ssh / scp / sftp etc.) ssh admin@mailhost.tinynet.edu
To Not use multiplexing for this session ssh -o 'ControlMaster=no' admin@mailhost.tinynet.edu
To check the status of multiplexing ssh -O check admin@mailhost.tinynet.edu
To gracefully shutdown multiplexing ssh -O stop admin@mailhost.tinynet.edu
To remove the control socket and
immediately terminate existing connections 		ssh -O exit admin@mailhost.tinynet.edu


Setting up Key Based Authentication

OpenSSH server supports various authentication schemes: Password and Public Key are the most popular.

Using key based authentication you can log into a server without having to enter your account password. This can be convenient for using tools like multitail, but it takes a bit more work to set up:
  1. Create a key pair on the local (client) host for the server
  2. Copy the public key to the remote (server) host
  3. Install the public key on the remote (server) host
  4. Add a passphrase to ssh-agent on the local (client) host
  5. Add some code to .bashrc on the local (client) host to run ssh-agent automatically when the user logs in
  6. Add AddKeysToAgent yes to the Host section of /etc/ssh/ssh_config on the local (client) host

1. Create a key pair on the local host for the server

It is possible (although not considered best practice) to use the same SSH key pair for multiple hosts. The better way is to use a distinct key for each host with the IdentitiesOnly and IdentityFile directives in a user-specific config file. See the ssh_config man page for a full description of these options.

An SSH key pair can be generated by running the ssh-keygen command. The man page says the default 2048-bit RSA (and SHA256) is "generally considered sufficient" and should be compatible with virtually all clients and servers.

You will be prompted for the desired name and location of your private key. By default, keys are stored in $HOME/.ssh/ and named according to the type of encryption used. When asked for the location, give a directory name that identifies the remote host to keep the keys organised.

You will be prompted to supply a passphrase (password) for your private key. Use something that conforms to the rules for strong passwords.

If you want to change the passphrase for the private RSA key later, use (with the name of your actual public key file)
ssh-keygen -f ~/.ssh/id_rsa -p

2. Copy the public key to the remote server

The ssh-copy-id script (and man page) is useful if you have a lot of servers to update on a regular basis, but all the options are rather confusing. Much easier to simply just copy the public key (id_rsa.pub) to your home directory on the remote server with [F9] [Shell Link] in mc - just remember that you can copy from but not to the remote host.

Or you can use the ssh copy command: scp ~/.ssh/id_rsa.pub username@remote-server.tld:
Be sure to use the actual name of the file you want to copy, and be sure to include the : at the end of the server address. Provide the password for your remote user account when prompted.

3. Install the public key on the remote server

To install the public key you just copied, login on the remote server and create a .ssh directory in your home directory if it does not exist. Append your public key to the list of authorized_keys like this: cat ~/id_rsa.pub >> ~/.ssh/authorized_keys and delete id_rsa.pub from your home directory.

Finally, ensure that you have the proper permissions set on all relevant files: they should only be readable and writeable by you, the owner. 

For the local (client) system:
    chmod 700 ~/
    chmod 700 ~/.ssh
    chmod 600 ~/.ssh/id_rsa

For the remote (server) system:
    chmod 700 ~/
    chmod 700 ~/.ssh
    chmod 600 ~/.ssh/authorized_keys
Now test the setup: connect as usual, and you should be prompted for the passphrase for the private key that you specified in Step One. To get rid of passphrase whenever you log in the remote host, move on to the next step.

4. Add a passphrase to ssh-agent on the local host

When your private key is encrypted with a passphrase, this passphrase must be entered every time you attempt to connect to an SSH server using public-key authentication. An SSH agent is a program which caches your decrypted private keys and provides them to SSH client programs on your behalf. In this arrangement, you only provide your passphrase once, when adding your private key to the agent's cache. This can be quite convenient when making frequent SSH connections. ssh-agent is the default agent included with OpenSSH. When it is run from the command line, it forks to the background and prints necessary environment variables.

To make use of these variables, run the command through the eval command: eval $(ssh-agent)

Once ssh-agent is running, you need to add your private key to its cache: ssh-add ~/.ssh/id_rsa
(enter the passphrase when prompted)

Once your private key has been successfully added to the agent you will be able to make SSH connections without having to enter your passphrase.

5. Configure the user startup file to run ssh-agent automatically when they log in

An agent is typically configured to run automatically upon login and persist for the duration of your login session. Adding the following code to ~/.bashrc will start ssh-agent automatically and make sure that only one instance will be running.

if ! pgrep -u "$USER" ssh-agent >/dev/null; then
   ssh-agent > ~/.ssh-agent-values
fi
if [ "$SSH_AGENT_PID" == "" ]; then
   eval "$(<~/.ssh-agent-values)"
fi
Line 1:
  • pgrep -u "$USER" ssh-agent looks through the process list ((like htop)) for a process named ssh-agent owned by the current USER
  • >/dev/null means don't show any output from the command to the user
  • if ! .... ; then means if the condition ... is NOT ! true, do the next steps until there is an else or fi
Line 2:
  • When ssh-agent is run from the command line, it prints some environment variables, so ...
  • Run it and send the output > to a file in the current user's home directory ~/ named .ssh-agent-values
Line 4:
  • When ssh-agent starts it stores its numeric process id to the environment variable SSH_AGENT_PID
  • if the value of $ the environment variable is NULL "" then
Line 5:
  • Run the eval command to set the environment variables "$( ... )"
  • Use the data stored in the file < in the current user's home directory ~/ named .ssh-agent-values
So, this will run a ssh-agent process if there is not one already, and save its output. If there is one running, retrieve the saved output and evaluate it to set the necessary environment variables. Note that if you change the .bashrc in etc/skel then every new user will have it available.

6. Configure the user startup file to run ssh-agent automatically when they log in

Putting AddKeysToAgent yes in the Host section of /etc/ssh/ssh_config will make all ssh clients store keys in the agent on first use. Note that you need to change .bashrc as described above before the AddKeysToAgent directive will take effect.

Testing

Once you have Multiplexing or Key Based Authentication set up, test the connection with a simple "Here Document" like this: (See Script I/O under Standard I/O on the menu)

ssh -T user@host.com << EOF
echo "The current local working directory is: $PWD"
echo "The current remote working directory is: \$PWD"
EOF

Final Notes

If it appears that the SSH server is ignoring your keys, check the permissions. If that does not solve the problem you may try temporarily setting StrictModes no in sshd_config. If authentication with StrictModes off is successful, it is likely that you still have an issue with file permissions.

Use debug mode and monitor the output while connecting: /usr/bin/sshd -d

To backup an existing private/public key, just copy the files to your backup server or external USB drive.

Protect your ssh keys: (*) Always use a strong passphrase, (*) Restrict privileges, (*) Do not share your private keys anywhere online or store in insecure cloud storage.

There is a nice discussion of ssh encryption algorithms and other agents at https://wiki.archlinux.org/index.php/SSH_keys
